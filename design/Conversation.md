# Conversation History and Compaction Design Document

- Status: implemented
- Parent document: `DESIGN.md` (§5.7, §5.10)
- This document details the design in which the LLMClient holds the Chat
  Completions message history for the entire session and compacts it via
  compaction once it grows too long.

---

## 1. Overview / Division of Memory Roles

`LLMClient` owns the Chat Completions message history. The history starts with
the system prompt, and all queries, tool calls, tool results, and final
responses in the session accumulate contiguously:

```
[system: SYSTEM_PROMPT]                     ← fully static
[user: query 1 (full screen + Goal)]
[assistant: tool_calls=...]
[tool: execution result] ...
[assistant: final explanation]
[user: query 2 (the delta of new output between queries + Goal)]
...
```

| Memory | Substance | Coverage |
|------|------|-----------|
| Conversation memory | Message history (held by the client) | Everything the LLM has seen/done |
| Screen memory | The delta of new output sent per query (§3) | The user's manual actions between queries |
| Compacted memory | Handoff summary at compaction time (§5) | Context when discarding the history and moving to a new conversation |

## 2. Prompt Cache Invariants

The prompt cache only applies on an exact prefix match. Except immediately
after compaction, **every request must be a strict extension of the previous
request**; the following rules ensure this:

- The history is **append-only**. Past messages are never rewritten. Assistant
  responses are appended to the history exactly as returned (the `arguments`
  of `tool_calls` keep the raw string generated by the model).
- The `system` prompt, `tools` definitions, `parallel_tool_calls=False`, and
  model are completely fixed across requests.
- Compaction requests are issued with the same system and tools (§5).
- Injecting a session summary into the system prompt is not adopted, because
  every summary update would invalidate the cache for the entire history
  (the summary is used only at compaction time; §5).

The test `test_history_is_append_only_across_requests` verifies this invariant
(the messages of a later request have the messages of the previous request as
a prefix).

## 3. Interface as Seen from the Executor (compaction is transparent)

```python
class LLMStepper(Protocol):
    async def start_query(query, *, screen_text, new_output=None, on_delta=None) -> StepResult
    def add_tool_output(call_id: str, output: str) -> None   # synchronous, local append
    async def step(on_delta=None) -> StepResult
    def finish_query() -> None    # notifies end of query execution (synchronous; triggers compaction)
```

- On every query the Executor passes **both** `screen_text` (the full screen
  via `get_text(history_lines)`) and `new_output` (the delta since the
  `mark()` at the end of the previous execution). The LLMClient decides which
  to use:
  - **New conversation** (first in the session / right after compaction):
    "(Session Summary +) Current Terminal Screen + Goal" — full-screen context
    is not lost even after compaction
  - **Ongoing conversation**: "New Terminal Output (the delta) + Goal" — past
    screens are already in the history, so they are not resent. If the delta
    is empty, the section is omitted
- The delta is capped by the Executor at `new_output_max_chars` (default
  20000 characters). When exceeded, the head is cut while keeping the tail
  (the most recent output closest to the query), and a
  `[... earlier output truncated ...]` note is added.
- The Goal goes at the end of the message (recency).

## 4. Recording Tool Results (history consistency)

Chat Completions requires that an assistant's `tool_calls` be followed by
corresponding `tool` messages. Since `add_tool_output()` became a synchronous
local operation, the Executor can **always record on every path**:

- Normal execution → the output after settle
- Declined at the confirmation gate → DECLINED
- Invalid arguments / unknown tool → Error text
- **Ctrl-C while waiting for settle** → the screen output up to that point +
  an interrupted note (recorded synchronously in the except clause of
  `_run_tool_call` before re-raising)
- Interruption before execution starts → a boilerplate interrupted output
  (`execute()` fills in the unprocessed calls)

Even when execution ends at a checkpoint stop, the completed portion has
already been recorded, so the next query can simply continue.

## 5. Compaction (internal to LLMClient, transparent to the Executor)

The history is sent in full and billed in full on every request (with cache
discounts), so it cannot grow without bound.

- **Trigger**: immediately after a query's execution ends (after the
  explanation is displayed and control is returned to the user). The Executor
  calls the synchronous `finish_query()` in the finally block of `execute()`
  (fires on normal completion, checkpoint stop, and interruption alike), and
  if the threshold is exceeded, the LLMClient starts compaction as an
  **asyncio background task**. The task actually runs after the execution
  task completes, i.e. after returning to passthrough, so the user is not
  kept waiting.
- **Decision**: the most recent response's `usage.prompt_tokens` is at or
  above `compact_thresh` (config, default 100000). As a fallback for backends
  that do not return usage, it is estimated as the history's character count
  divided by 4.
- **Procedure**: with the current history + COMPACT_REQUEST (a user message),
  call `chat.completions.parse(response_format=HandoffSummary,
  tool_choice="none")` once. The system and tools are kept identical to
  normal steps, so the prefix cache for the history (the largest prompt of
  the session) still applies. On success, the history is reset to `[system]`
  and the summary is retained.
- **Synchronization with the next query**: `start_query()` waits for any
  in-flight compaction task to complete (while `[thinking...]` is displayed),
  then includes the retained summary in the first message as "Session Summary
  + full screen + Goal". A Ctrl-C during query execution interrupts this
  wait, but the compaction task itself runs to completion independently and
  the next query picks up the result.
- **On failure**: the history is kept (no compaction happens) and a retry is
  attempted at the end of the next query (context is not discarded during API
  outages). Errors are recorded in the JSONL log. The background task never
  leaks exceptions.

## 6. config (config.toml top level)

| Key | Default | Meaning |
|------|--------|------|
| `compact_thresh` | 100000 | If the most recent response's prompt_tokens is at or above this, compact after the query ends |
| `new_output_max_chars` | 20000 | Maximum character count of the between-query delta (truncation keeping the tail) |

## 7. Constraints (accepted trade-offs)

1. Manual output that flows between queries in excess of
   `new_output_max_chars` is not passed to the LLM. A truncation note merely
   signals the omission.
2. Likewise, interaction history scrolled beyond `history_lines` before the
   first query is not passed. Having `history_lines` lines of screen at the
   first query is judged sufficient in practice.
3. Thinking tokens of reasoning models are not carried across turns
   (a Chat Completions limitation).
4. What compaction loses is only the LLM's own intermediate thoughts and
   explanations; the facts on the terminal are covered by the summary plus
   the full screen.

## 8. Candidate Future Extensions

- Adding a token/cost budget cap (SWE-agent style) alongside (DESIGN.md §9).
- Partial compaction that thins out only old tool results in the history
  (currently full reset only).
